**ADR-004 ·  Resiliencia y modos de falla**

**Estado:** Aceptada

**Contexto:** ¿Qué pasa cuando el Catálogo está caído, o lento? ¿Qué código de estado devuelve la API y por qué? ¿Qué se ganaría con caché o con un timeout, y qué se perdería?. En un entorno distribuido, el servicio de habitaciones puede sufrir caidas o degradaciones de red (latencia alta). Se requiere determinar el comportamiento de la API REST para manejar esto.

**Alternativas consideradas:**
* *Opción A:* Llamadas síncronas sin límite de tiempo (espera indefinida) y sin compensación transaccional.
* *Opción B*: Mecanismo de caché distribuida agresiva para disponibilidad de habitaciones (evita llamadas, pero arriesga sobreventa o inconsistencia crítica en inventario).
* *Opción C*: Timeout estricto en gRPC, manejo de fallas controladas con estado de REPARACION, códigos HTTP semánticos (409 y 503) y compensación / rollback explícito (Saga).   

**Decisión:** Opcion C. Timeout estricto de 2s por llamada gRPC, cascadas de rollbacks inmediatas ante reservas mal procesadas y se les coloca el estado de `REPARACION` con respuesta 503 ante fallos de conectividad. 

**Justificación:** 
- En grafico_timeout.png (caída abrupta de proceso / container stop), la latencia promedio en caida_2s, caida_5s y caida_10s se mantiene en el orden de milisegundos (< 50 ms), ya que el canal TCP es cerrado inmediatamente por el sistema operativo devolviendo UNAVAILABLE al instante.

- En contraste, en grafico_timeout_pause.png (demora de red o contenedor pausado sin cerrar sockets), se observa que si no hubiera timeout estricto, la API quedaría retenida linealmente al tiempo de retención (2000 ms, 5000 ms y hasta 10000 ms). El límite de timeout=2.0s corta la espera en $2000\text{ ms}$, evitando el agotamiento de sockets y la degradación en cascada de reservas-api.   

- Se devuelven los códigos 409 Conflict cuando habitaciones responde no disponible. `503 Service Unavailable` cuando expira el timeout.

**Costo aceptado:** Si ocurre un corte justo despues de que Habitaciones guardo una asignación pero antes de responder, la reserva queda en estado de `REPARACION` hasta que se ejecute alguna resolución.

**Consecuencias:** Resiliencia de alto nivel y estabilidad del servicio frente a caidas internas. Trazabilidad completa de reservas dudosas sin bloqueos silenciosos.
