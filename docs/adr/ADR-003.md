**ADR-003 · Contrato, versionado y evolución**

**Estado:** Aceptada

**Contexto:**
Se debe establecer una estrategia formal de versionado, compatibilidad hacia atrás (*backward compatibility*) y evolución de contratos tanto para la API REST pública orientada a clientes externos como para el servicio gRPC interno.
Las preguntas fundamentales de arquitectura a resolver son:
1. ¿Cómo evolucionaría el contrato si mañana hay que agregar un nuevo campo o método?
2. ¿Qué cambios se consideran compatibles hacia atrás y cuáles exigirían una versión mayor nueva?
3. ¿Cómo se enteran los consumidores de las modificaciones sin riesgo de caídas imprevistas?

**Alternativas consideradas:**
* *Opción A (Sin versionado formal / Contrato vivo):* Evolución continua sobre un único endpoint y esquema sin prefijos ni namespaces. Aunque ahorra mantenimiento de versiones paralelas, introduce un altísimo riesgo de romper clientes en producción ante modificaciones de tipos o eliminación de campos.
* *Opción B (Versionado semántico por ruta en REST y namespaces en Protocol Buffers):* Versionado mayor explícito en la URI para REST (`/v1`) y namespaces de paquetes versionados en Protocol Buffers (`package hotel.habitaciones.v1;`), junto con directrices estrictas de compatibilidad aditiva.

**Decisión:**
Se adopta la **Opción B**. Se establece versionado por ruta `/v1` para la API REST pública y versionado de paquete `hotel.habitaciones.v1` en los contratos Protobuf.

**Justificación:**

* **Evolución y compatibilidad en gRPC / Protocol Buffers (`contracts/habitaciones.proto`):**
  * **Serialización basada en etiquetas (*Field Tags*):** Protobuf serializa mediante números enteros de campo (1, 2, 3...) y no por nombres de variables. Esto desacopla el identificador binario de la representación textual.
  * **Adición de nuevos campos (Cambio Compatible):** Todo campo nuevo se declara como opcional (`optional` o semántica nativa de Proto3) asignándole un nuevo número secuencial nunca antes utilizado. Por ejemplo, en el código real se incorporó `optional int32 habitacion_id = 4;` a `AsignarHabitacionRequest` para permitir asignación híbrida; los clientes antiguos que solo envían los tags 1, 2 y 3 continúan operando sin ninguna alteración ni error de compilación.
  * **Eliminación y obsolescencia de campos:** Si un campo se depreca, nunca se borra ni se reutiliza su etiqueta numérica; se marca explícitamente como `reserved <tag_number>, "<field_name>";` para prevenir que futuras versiones asignen dicho tag a un nuevo tipo de dato, lo que causaría corrupción binaria silenciosa.
  * **Preservación de campos desconocidos (*Unknown Fields*):** Proto3 preserva los bytes de campos con tags no reconocidos por stubs antiguos, garantizando que un intermediario o componente desactualizado no descarte datos durante el reenvío.
  * **Ruptura de contrato y nueva versión mayor:** Si se requiere un cambio destructivo (como alterar la firma de un RPC, cambiar los tipos de datos primarios o modificar la semántica de la reserva), se crea un nuevo paquete `package hotel.habitaciones.v2;` con un nuevo servicio `HabitacionesServiceV2`. El servidor gRPC puede registrar ambos servicers simultáneamente en el mismo puerto `50051`, permitiendo que microservicios llamadores migren gradualmente a su propio ritmo sin *downtime*.
  * **Comunicación a consumidores:** El contrato `contracts/habitaciones.proto` es la fuente única de verdad. Los cambios se gestionan mediante versionado en Git y compilación de stubs independientes en `reservas/app/protos/` y `habitaciones/app/protos/`.

* **Evolución y compatibilidad en REST / OpenAPI (`contracts/openapi.yaml` y `reservas/app/`):**
  * **Cambios compatibles (Aditivos):** La incorporación de nuevos endpoints (como `POST /v1/reservas/{id}/resolver`), la inclusión de cabeceras opcionales (como `Idempotency-Key` o `X-API-Key`) o la adición de nuevos atributos en las respuestas JSON (como enlaces HATEOAS `_links` o detalles informativos de habitaciones) son retrocompatibles, ya que los clientes ignoran claves no contempladas.
  * **Cambios incompatibles (Breaking Changes):** Renombrar o eliminar parámetros obligatorios en solicitudes, modificar el formato de fechas (alejándose del estándar semiabierto `YYYY-MM-DD`), o alterar la estructura canónica de errores JSON (`{"error": {"tipo": "...", "mensaje": "..."}}`) rompería a los clientes externos.
  * **Estrategia de versionado mayor:** Ante cambios destructivos, se monta un nuevo enrutador bajo `/v2` en FastAPI (`app.include_router(router_v2, prefix="/v2")`), manteniendo `/v1` completamente operativo durante una ventana de deprecación anunciada.
  * **Comunicación a consumidores:** La API expone su documentación interactiva actualizada en tiempo real vía Swagger UI (`/docs`) y el esquema OpenAPI formal en `contracts/openapi.yaml`. Se utilizan cabeceras HTTP estándar de deprecación (`Deprecation: true`, `Sunset: <fecha>`) para alertar oportunamente a los consumidores externos.

**Costo aceptado:**
Si un cambio de negocio exige una nueva versión mayor (`/v2`), el equipo debe asumir la sobrecarga operativa de mantener simultáneamente los endpoints y controladores antiguos junto a los nuevos durante el periodo de transición.

**Consecuencias:**
Se garantiza estabilidad absoluta en producción. Los clientes externos y los microservicios internos que no requieran las nuevas características pueden seguir funcionando sin interrupciones ni fallos imprevistos ante las mejoras incrementales de la plataforma.
