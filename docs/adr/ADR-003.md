**ADR-003 ·  Contrato, versionado y evolución**

**Estado:** Aceptada

**Contexto:** ¿Cómo evolucionaría el contrato si mañana hay que agregar un campo? 
¿Qué cambios serían compatibles y cuáles exigirían una versión nueva? ¿Cómo se enterarían los consumidores?
Se debe establecer una estrategia de versionado, backwards compatibility y evolución de contratos para la API REST pública con el gRPC interno, minimizando problemas cuando surjan nuevos requerimientos.

**Alternativas consideradas:**
* *Opción A:* Sin versionado explicito, contratos evolucionando de manera incremental y continua.
* *Opción B:* Versionado semántico con versionado segun la ruta para REST y paquetes de Protobuf, junto a reglas de backward compatibility.

**Decisión:** Opcion B. Versionado en la URI para la API REST (/v1) y versionado de paquete Protobuf.

**Justificación:** 
- En gRPC: FALTA JUSTIFICAR
- En REST: Agregar atributos a las respuestas JSON no causa problemas de compatibilidad, en caso de renombrar endpoints, eliminar atributos o alterar el formato de input se puede cambiar el prefijo a `/v2` y mantener la versión anterior.

**Costo aceptado:** Si un cambio de negocio exige una nueva versión mayor, se deben mantener simultaneamente los endpoints y los controladores antiguos durante la migración.

**Consecuencias:** Se garantiza que los clientes externos desactualizados no sufran fallos imprevistos con las mejoras incrementales de la plataforma
